# HackRF Capture Provenance V1

Status: PRE-IMPLEMENTATION SPECIFICATION

## Purpose

Define the provenance requirements for Hardsignal Labs Wider-IQ V1
HackRF CS8 acquisitions.

This provenance layer records acquisition facts. It does not perform
device identification, classification, RF attribution, or waveform
interpretation.

## Relationship to Wider-IQ V1

The HackRF acquisition mechanism was frozen before S1/S2 Wider-IQ V1
development collection.

Frozen receiver configuration:

- receiver: independent HackRF One;
- center frequency: 433868160 Hz;
- complex sample rate: 2000000 samples/s;
- baseband filter: 1750000 Hz;
- representation: interleaved signed int8 I,Q (CS8);
- RF amplifier: OFF;
- antenna port power: OFF;
- LNA gain: 32 dB;
- VGA gain: 32 dB.

The running KrakenSDR system remains independent and unchanged.

## Capture unit

One provenance bundle represents one HackRF acquisition.

Each completed bundle shall contain:

- manifest.json
- files.sha256
- activation.log
- hackrf_transfer.log
- notes.md

Raw CS8 data remain outside Git.

## Manifest format

Format identifier:

HARDSIGNAL_HACKRF_CAPTURE_MANIFEST_V1

Required manifest fields:

- format
- capture_id
- sensor_label
- engineering_only
- started_wall_utc
- finished_wall_utc
- started_monotonic_ns
- finished_monotonic_ns
- git_head_at_start
- git_head_at_finish
- receiver
- acquisition
- tool_versions
- command
- transfer_exit_code
- expected_complex_samples
- expected_size_bytes
- actual_size_bytes
- sha256
- raw_file
- activation_log
- transfer_log

## Receiver provenance

Receiver metadata shall preserve the output required to identify the
HackRF used for acquisition, including available:

- board type;
- serial number;
- firmware version;
- hardware revision;
- hackrf_info/libhackrf version.

Hardware provenance is descriptive only.

## Acquisition command

The receive command shall be generated by the capture tool from frozen
constants rather than entered manually for V1 evidence.

The command shall use receive mode only.

Frozen parameters:

- frequency: 433868160 Hz
- sample rate: 2000000 samples/s
- baseband filter: 1750000 Hz
- RF amplifier: 0
- antenna port power: 0
- LNA: 32 dB
- VGA: 32 dB

The V1 evidence path must not expose a transmit operation.

## Sample representation

hackrf_transfer raw receive output is treated as interleaved signed
8-bit I,Q.

Therefore:

expected_size_bytes = expected_complex_samples * 2

A completed capture fails provenance verification if actual size differs
from the expected size.

## Timing

The wrapper shall record both:

- timezone-aware UTC wall-clock timestamps;
- Python monotonic_ns timestamps.

Operator activation markers shall also contain wall-clock and monotonic
timestamps.

Operator markers represent the time the operator pressed ENTER while
triggering the controlled source. They are not exact RF-emission
timestamps.

## Activation log

The activation log is mandatory for controlled V1 evidence.

It shall identify:

- capture ID;
- sensor label;
- expected activation count;
- quiet interval;
- each activation label;
- wall timestamp;
- monotonic_ns timestamp.

The logger must flush every marker immediately.

## Transfer log

stdout/stderr from hackrf_transfer shall be preserved.

The transfer exit code shall be recorded in the manifest.

A non-zero transfer exit code fails verification.

## Integrity

The completed raw CS8 file shall have:

- expected byte count;
- actual byte count;
- SHA-256.

files.sha256 shall contain hashes for the raw CS8 file and provenance
sidecar files selected by the implementation.

The verifier shall recompute raw-file size and SHA-256.

## Git provenance

Git HEAD shall be recorded immediately before and after acquisition.

A HEAD change during acquisition shall be reported by the verifier.

## Sensor labels

Sensor labels are operator-supplied experimental labels.

For Wider-IQ V1 development, only protocol-authorized labels may be used.

Engineering validation captures must be explicitly marked
engineering_only=true.

## Failure handling

The tool must preserve failed and incomplete acquisition evidence where
possible.

It must not silently convert an interrupted, short, failed, or malformed
capture into a valid capture.

It must never overwrite an existing capture bundle or raw CS8 file.

## Verification requirements

A completed V1 capture passes provenance verification only if:

- manifest format is correct;
- transfer exit code is zero;
- frozen acquisition parameters match exactly;
- raw file exists;
- expected and actual byte counts agree;
- raw SHA-256 agrees;
- activation log exists;
- transfer log exists;
- Git provenance is present;
- required timing fields are present.

Experimental interpretation remains separate from provenance validity.

## Development boundary

This specification and its implementation must be validated using
engineering-only data before the first S1 or S2 Wider-IQ V1 development
capture.

No S1/S2 V1 data may be collected merely to test the provenance tooling.
